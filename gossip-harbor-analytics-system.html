Reading this report#

This is a static, source-backed analysis of the extracted Android client. It describes what the client is built to do; it does not claim that every packaged SDK is active for every player, that every conditional event fires in production, or that a backend accepts and uses every submitted field.

Evidence labels used throughout:

  • Direct: readable Lua shows the runtime call or implementation.
  • Bridge: an exported C# or native-facing interface shows the capability, but the implementation is not visible.
  • Packaged: files or assemblies are present in the app package; runtime use is not established by that fact alone.
  • Inferred: the purpose follows from event names, payloads, and call sites, but is not stated as a formal product requirement.
  • Not evidenced: the searched extraction contains no reliable proof of the claimed integration or behavior.

Paths in citations are relative to the Gossip Harbor 3.95.0 extraction root. In inline citations, .../core, .../base, .../activity, and .../test abbreviate 05_gameplay_logic/lua/readable/decompiled/; 02_exported_core/.../OneSDK abbreviates 02_exported_core/ExportedProject/Assets/Scripts/Assembly-CSharp/OneSDK. Appendix C gives the full paths. Line numbers refer to this extracted build and may not transfer to other versions.

Part I — High-Level Understanding#

1. Executive summary#

Gossip Harbor 3.95.0 uses a broad, layered analytics system rather than a single analytics SDK. Its center is a first-party Lua component named BIManager. Gameplay, economy, user-interface, purchase, advertising, network, session, and performance code call this manager throughout the client. A static search finds 1,067 GM.BIManager:<method> call-site lines across 373 Lua files, including 1,023 Log* call-site lines across 370 files. These counts measure static instrumentation breadth, not runtime event volume.

The first-party pipeline enriches most events with shared player and app context, queues them in dot_message.dat, batches them, and hands a complete request to HttpManager for retry. Both stages have later save cycles. HttpManager adds the request to CachedRequests before calling Send, but does not force a disk commit at that point; BIManager clears its event queue immediately after the send call. A crash before the next save can therefore lose an event or request. Conversely, an accepted request whose response is lost can be retried and counted twice unless the backend deduplicates it. (05_gameplay_logic/lua/readable/decompiled/core/Model/Network/BI/BIManager.lua:55-102,730-753; .../core/Model/Network/HttpManager.lua:85-168; .../core/Model/DB/DBTableManager.lua:43-64,84-100)

The client also routes selected marketing and platform events outside the first-party BI path. AppsFlyer is directly used for installation, attribution identity, conversion/deep-link data, purchases, and server-mapped events. Firebase is directly used for analytics identity/properties and mapped events; its Crashlytics-facing API receives diagnostic keys and log breadcrumbs. Platform bridge calls provide a further attribution/event route, including China-specific BDA behavior. Google UMP is used for advertising consent, while advertising is mediated behind a generic OneSDK ad bridge. AppLovin MAX and several mediation adapter resources are packaged, but readable Lua does not select or initialize each adapter directly.

No Adjust SDK integration is evidenced in the searched build. The client contains legacy fields named adjust and adjust_id, but adjust_id is explicitly populated with the AppsFlyer ID, while adjust carries a server-provided mapping whose destinations are AppsFlyer and Firebase. Searches found no Adjust package, assembly, namespace, configuration object, event object, or API call. Adjust should therefore not appear in a toolkit diagram as an active SDK for this build.

Privacy is not represented by one universal gate. The fresh global-build dialog acceptance calls Firebase SetConsent; returning accepted users skip that Lua call. The non-global acceptance path starts BDA, and an existing-user bypass can start BDA without a visible region check. On a fresh install, startup logs a session_start with detailed device context and the low BI ID triggers an immediate reqCtx:Send() before the visible privacy-policy check. Global startup also calls Firebase/Crashlytics setup before that check. Actual network egress and native SDK consent enforcement remain unverified. Advertising follows a separate UMP path, but Lua initializes the ad manager before UMP and does not visibly gate rewarded-ad loading on CanRequestAds. (.../core/Model/GlobalManager.lua:119-129; .../core/Model/Network/BI/BIManager.lua:55-96,558-566; .../base/Main.lua:80-89; .../core/Model/GameModel.lua:375-422; .../core/Model/AdModel.lua:31-35,199-223)

The system is designed to answer product questions about onboarding, progression, merge-board behavior, resource flows, offers and purchases, rewarded ads, activities, UI navigation, reliability, performance, and acquisition. The strongest governance concerns are the volume of default enrichment, requested device identifiers on session events, purchase and ad-revenue context, an active conditional push-token BI path, and code paths capable of carrying social login/profile values. A sensitive SDK-login wrapper exists, but no live Lua call site was found for it; it should be treated as a risky capability, not as proven production transmission.

4. High-level data flow and destinations#

There are several parallel flows.

  1. First-party product BI: a gameplay or UI call invokes a typed BIManager wrapper; the wrapper constructs a record; LogWithInfo adds optional economy state; _AppendBIInfo adds common app/player/device context; QueueMessage adds the JSON event to a local dictionary; FlushMessages makes an envelope; HttpManager caches the full HTTP request; the request is sent to a OneSDK-provided BI URL and retried when necessary. Queue and database writes are committed on later save cycles.

  2. Operational marketing routing: OperBIManager emits named install/purchase events and uses a server response to map selected level or purchase IDs to AppsFlyer and Firebase event names. This is a separate route from the first-party BI upload, even when the same player action also generates a first-party event.

  3. Platform-standardized events: progression, resource, shop, purchase, and tutorial flows call platform bridge APIs such as SDK_TrackEvent or Attr_TrackEvent. The exported bridge reveals the interface but not every final vendor destination.

  4. Diagnostics: performance BI goes to the first-party/profiler path; selected context is also written as Crashlytics keys or breadcrumbs.

  5. Advertising measurement: ad state and reward outcomes create first-party BI records. The native ad facade additionally returns mediation-network and paid-event details, which Lua aggregates and logs.

As a result, one business action can generate multiple records. After purchase verification and fulfillment reach the final success block, the client creates first-party pay/pay-action events and may create server-mapped AppsFlyer/Firebase events. Non-mini-game code sends IAP proof traffic, calls AppsFlyer client_purchase and a hard-coded abc event, and logs abc to Firebase on global builds. Mini-game code instead records/confirms the order and sends a platform attribution purchase event. Reconciliation depends on shared user/order/product fields and backend conventions that are not visible. (.../core/Model/InAppPurchase/InAppPurchaseModel.lua:394-429; .../core/Model/Network/Oper/OperBIManager.lua:11-18,73-95)

5. Identity, attribution, and consent overview#

Identity layers#

The client uses several identifiers with different roles:

  • Game account identity: numeric user ID and authentication token when available.
  • Installation identity: an installation UUID and a locally incremented BI ID.
  • Vendor identity: AppsFlyer ID and CUID, Firebase user ID/instance ID, and regional click IDs.
  • Platform/device identity: IDFV/vendor ID, advertising ID, Android/device IDs, OAID/CAID in applicable paths, and some legacy hardware/network identifiers exposed by the bridge.
  • Transaction identity: product ID and order ID, plus receipt/signature values in payment-proof traffic.

Most first-party BI events receive installation, build, time, network, country, and optional user identity. The detailed device-information block is requested by session events, network diagnostics, and LogAction calls whose action is init. Native privacy restrictions can cause some values to be unavailable even though the code asks for them. (.../core/Model/Network/BI/BIManager.lua:224-239,538-566,627-707)

Consent timing#

  • On the fresh global dialog-acceptance path, Lua calls Firebase SetConsent and requests ATT. Remembered acceptance and the existing-user bypass skip the Lua SetConsent call; native persistence of consent is unknown. (.../core/Model/GameModel.lua:375-422)
  • The non-global acceptance path starts BDA. The existing-user bypass also starts BDA without a visible region condition. (.../core/Model/GameModel.lua:385-420)
  • Advertising has a separate UMP process. The ad manager initializes before UMP, the form is optionally requested when AdPrivacyOpen is enabled, and CanRequestAds is logged immediately after that request. Lua does not visibly use it to gate ad loading. (.../core/Model/AdModel.lua:14-36,199-230)
  • On a fresh install, the first session_start reaches an HTTP Send call before the visible privacy-policy check. Firebase/Crashlytics setup calls also occur before that check. Static code does not establish actual network egress or native consent enforcement.

Attribution#

AppsFlyer is the only named mobile measurement partner whose identity and event APIs are both packaged and directly invoked. Its media source, tracker, conversion data, attribution data, deep-link data, and AppsFlyer ID are also copied into first-party or operational records. China-specific attribution uses BDA/CAID-style context through the platform bridge. The generic platform attribution path may fan out natively, but the exported client does not identify all destinations.

6. Key findings, risks, and unknowns#

High-confidence findings#

  • Analytics is deeply embedded in gameplay and operations, with hundreds of instrumented Lua files and a large event catalog.
  • The first-party pipeline has an event queue and a cached-request retry table, both with later persistence cycles; it has a crash-loss window before a save completes.
  • AppsFlyer is directly used; Firebase analytics/Crashlytics APIs are directly called; UMP is directly orchestrated for ad consent.
  • The server can change selected AppsFlyer/Firebase event mappings and the BI compression mode without a client release.
  • No Adjust SDK use is evidenced in Gossip Harbor 3.95.0.
  • Client-side content deduplication and FIFO ordering are not guaranteed by the visible code.
  • The level-up action sent to first-party BI uses a level one higher than the newly stored level passed to operational routing and, on global builds, Firebase.

Main risks#

  1. Consent-ordering risk: on a fresh install, first-party session_start invokes HTTP Send before the visible policy flow; Firebase/Crashlytics setup also occurs early. Native egress and consent gates need runtime verification.
  2. Data-minimization risk: ordinary BI enrichment is broad, while selected diagnostic/login/payment paths can contain device, advertising, account, social, network, or transaction identifiers.
  3. Delivery risk: the client can lose a queued event or cached request before a save, or resend a request after an ambiguous result. Backend idempotency and crash-window testing are essential.
  4. Taxonomy-governance risk: a very large catalog, dynamic strings, and server-mapped destination names can drift without a central data contract.
  5. Multi-destination reconciliation risk: the same action can reach first-party BI, AppsFlyer, Firebase, Crashlytics, and platform routes with different naming and fields. The level-up path has a concrete one-level value mismatch.
  6. Static-analysis boundary: native SDK configuration, actual consent defaults, resolved endpoints, backend processing, and runtime event frequency are unavailable.

Highest-value validation questions#

  • Does any first-party, AppsFlyer, Firebase, Crashlytics, BDA, or ad request leave the device before explicit consent in each region/build mode?
  • Does the BI backend deduplicate using msg_id, and for how long?
  • Which fields are retained downstream, for how long, and under which regional policies?
  • Which packaged mediation adapters actually initialize and receive impression-level data?
  • Are social access tokens/profile fields ever passed through LogSDKLogin, or is that wrapper dormant?
  • Are dynamic event mappings versioned, reviewed, and documented with ownership?

Part II — Technical Deep Dive#

7. Initialization and analytics lifecycle#

GlobalManager constructs HttpManager, BIManager, the operational manager, and OperBIManager as application-level singletons. During Init, the managers are initialized and a session_start event is logged. BIManager.Init obtains the BI URL from NetworkConfig, opens dot_message.dat through SimpleStringDict, restores the local BI sequence, and registers for background notifications. (.../core/Model/GlobalManager.lua:15-129; .../core/Model/Network/BI/BIManager.lua:12-45; .../core/Model/Network/NetworkConfig.lua:62-66)

The main application Awake creates and initializes GlobalManager, then global-build code sets Crashlytics keys for version/mode and a Firebase idfa user property. The privacy-policy flow is invoked later from loading-layer progression. This produces the following observable Lua ordering:

  1. global managers are created and initialized;
  2. first-party session_start is queued and, on a fresh install with BI ID below 30, immediately reaches an HTTP Send call;
  3. Firebase/Crashlytics setup calls run on global builds;
  4. loading progresses;
  5. the visible privacy-policy decision is checked;
  6. fresh global dialog acceptance calls Firebase SetConsent; non-global acceptance starts BDA, while returning-user paths follow different branches.

This ordering and the first-party send call are direct Lua evidence. Whether native code allows actual network egress before consent remains unknown. (.../base/Main.lua:80-89; .../core/Model/Network/BI/BIManager.lua:32,55-96,558-566; .../core/UI/Layer/LoadingLayer.lua:177,455; .../core/UI/Layer/LoadingLayerNew.lua:302,655; .../core/Model/GameModel.lua:375-422)

On backgrounding, GlobalManager logs session_end, dispatches the background event, and the BI manager serializes its local state. On foregrounding it logs another session_start. Standard builds persist the BI ID and queue in LateUpdate; mini-game builds do so in a per-second update; destruction writes dirty data and closes the store. (.../core/Model/GlobalManager.lua:309-338; .../core/Model/Network/BI/BIManager.lua:730-753)

8. First-party BIManager architecture#

8.1 Layers#

The implementation can be divided into six client-side layers:

  1. Catalog: EBIType and EBIProjectType define most known event names.
  2. Domain wrappers: 35 Log* methods normalize the argument shape for actions, economy, merges, tasks, orders, purchases, ads, diagnostics, and other domains.
  3. Common enrichment: LogWithInfo and _AppendBIInfo add snapshot and identity/context fields.
  4. Event queue: each JSON event is added under a monotonically increasing pending key in a dictionary that is serialized to dot_message.dat later.
  5. Envelope and dispatch: pending JSON fragments are joined into an HTTP request body and assigned a message ID.
  6. Cached request delivery: HttpManager adds the complete request to a database table before sending, retries saved requests, and commits the table later.

8.2 Wrapper inventory#

The visible wrappers include:

Generic LogWithInfo, LogAction, LogString, LogUI
Economy LogUseItem, LogAcquire, LogStore
Board/core loop LogMerge, LogSplit, LogSpread
Progression LogTask, LogPassActivityTask, LogOrder, LogTutorial, LogActivity

The wrappers do more than rename events. They create stable field conventions for each domain before delegating to the shared enrichment and queue. (.../core/Model/Network/BI/BIManager.lua:157-626)

9. Event schema and automatic enrichment#

9.1 Event-specific fields#

Each wrapper creates a domain record. Examples include item ID/amount/reason for resource flows; source and target item state for merges; order state, slot, difficulty and rewards for orders; product/order/scene for the first-party LogPay event; and ad placement, result, and an ext string for LogAd. Price and currency travel through separate purchase/attribution paths. An ad-earned callback JSON-encodes revenue, currency, network, and country into LogAd.ext. (.../core/Model/Network/BI/BIManager.lua:211-269,298-307,355-370,609-618; .../core/Model/AdModel.lua:407-425)

9.2 Default gameplay snapshot#

Unless a caller disables it, LogWithInfo adds a snapshot of:

  • player level;
  • gold;
  • gems;
  • experience;
  • energy;
  • free gems;
  • purchased gems.

This makes most events independently segmentable by current economy state, but it also increases payload volume and the privacy/governance surface. (.../core/Model/Network/BI/BIManager.lua:157-199)

9.3 Common context#

_AppendBIInfo adds or can add:

Field group Visible values
Build/routing app version, channel ID, environment
Time client time and server-adjusted time
Network/platform network class and OS name
Installation/event identity install UUID, sequential BI ID, random value
Player/geography country and nonzero user ID
Optional device block OS version, model, language, MCC/MNC, IDFV, advertising ID, IMEI, device ID, MAC

The optional device block is requested by session events, network diagnostics, and LogAction(..., "init"), rather than every event. Several identifiers are subject to OS and consent restrictions, so a requested field may still be empty. (.../core/Model/Network/BI/BIManager.lua:224-239,538-566,627-707)

9.4 Envelope#

The queued JSON records are joined into an envelope shaped as follows. Example values are illustrative:

{
  "data": [{"event": "session_start", "bi_id": 1}],
  "msg_id": 123,
  "c_time": 1234567890,
  "token": "<game-token>"
}

The builder joins stored event JSON objects into data; it inserts numeric msg_id and c_time values without quotes. The request uses HTTP POST, an 8-second timeout, client/retry-client headers, and application/octet-stream. If the body exceeds 1,024 bytes and the operational service has supplied a nonempty compression method, the native compression hook is used. The compression algorithm is not visible. (.../core/Model/Network/BI/BIManager.lua:71-142; .../core/Model/Network/Oper/OperManager.lua:84-100)

10. Event taxonomy and domain coverage#

10.1 Catalog behavior#

BIDefine.lua contains the primary and project/diagnostic catalogs. During initialization, test-mode code checks for duplicate top-level string codes. If a requested key is missing, the system emits a project diagnostic once for that missing key and raises a test-mode error. This is a lightweight guard against silent taxonomy mistakes, but it is not a complete schema validator: it does not visibly enforce payload field names, types, requiredness, or destination parity. (.../core/Model/Network/BI/BIDefine.lua:1-1316; .../core/Model/Network/BI/BIManager.lua:34-44)

10.2 Coverage by business domain#

The catalog and call sites cover:

  • account, login, lifecycle, privacy, and notifications;
  • tutorial, level, task, order, pass, activity, and mini-game progression;
  • board item creation, acquisition, use, merge, split, spread, generators, obstacles, and rewards;
  • currency, energy, gems, gold, inventory, chests, and stores;
  • windows, buttons, offers, promotions, settings, and navigation;
  • purchase initialization, SDK stages, order query, receipt verification, success/failure, and first purchase;
  • rewarded ads, own-ad fallback, mediation network, reward, and paid-event revenue;
  • API timing/result, client errors, resource loading, device/storage/network state, startup, FPS, and frame hiccups;
  • attribution, conversion, deep links, campaigns, and server-controlled marketing mappings.

10.3 What the taxonomy does not prove#

  • A definition does not prove a call site.
  • A call site does not prove its branch executes.
  • Execution does not prove successful upload.
  • Upload does not prove backend acceptance or downstream use.
  • Similar names across first-party BI, AppsFlyer, Firebase, and platform routes do not prove identical semantics.

Those distinctions are why this report separates catalog, runtime call, bridge capability, package inventory, and backend unknowns.

11. Third-party and platform integrations#

11.1 OneSDK as the integration boundary#

Lua aliases multiple CS.OneSDK.* singletons, including platform, Firebase, Facebook, AppsFlyer, ads, install referrer, and related utilities. SDKManager exposes queues and callbacks for login, advertising, purchasing, install-referrer, and deep-link work. This makes OneSDK the native integration boundary rather than an analytics destination by itself. 12. Queueing, persistence, batching, and transport#

12.1 Pre-dispatch event queue#

The primary queue uses SimpleStringDict associated with dot_message.dat. Each enriched event is JSON-encoded and added under an incrementing pending key. The dictionary supports dirty tracking and later serialization; QueueData itself does not demonstrate an immediate disk write. (.../core/Model/Network/BI/BIManager.lua:1-5,55-70,730-753; .../base/Common/Utility/SimpleStringDict.lua:4-25,56-91,105-113)

Flush is triggered when either:

  • 10 unscaled seconds have elapsed; or
  • the pending count reaches 20.

For the first locally assigned BI IDs below 30, the code forces an immediate flush. Twenty is therefore a trigger threshold, not a demonstrated hard cap on envelope size: more than 20 may be present when the queue is flushed. (.../core/Model/Network/BI/BIManager.lua:46-61,695-698)

12.2 Post-dispatch saved request#

Before Send, the BI request is added to the CachedRequests table with:

  • URL;
  • HTTP method;
  • headers;
  • base64-encoded body;
  • operation name.

The event queue is cleared immediately after the Send call, not after server success. SaveHttpRequest updates the table cache but does not force a disk commit. DBTableManager flushes/commits later, leaving a crash-loss window between clearing the event queue and persisting the request. After persistence, a successful response removes the saved row; a non-success doubles its retry delay from the initial ten seconds. Saved requests are considered for resend only when the device is online and the game is outside loading and sync-upload states. (.../core/Model/Network/BI/BIManager.lua:84-102; .../core/Model/Network/HttpManager.lua:17-59,85-168; .../core/Model/DB/DBTable.lua:192-235; .../core/Model/DB/DBTableManager.lua:43-64,84-100)

12.3 Delivery semantics#

The visible design is a cached retry pipeline with periodic persistence, without an established at-least-once or exactly-once delivery guarantee:

  • a request is added to the cached table before the send attempt, but the disk save occurs later;
  • failures in a committed saved request remain eligible for retry;
  • an ambiguous result may cause the same request to be retried;
  • no visible client-side content deduplication occurs;
  • the envelope has a message ID that a backend could use for idempotency, but the backend is unavailable;
  • a crash before queue serialization or database commit, database failure, or app data deletion could cause loss.

12.4 Compression and endpoint resolution#

The BI endpoint comes from a native-facing GetOneSDKBIUrl() call and is cached by NetworkConfig. A response from the operational service can supply a compression method. Bodies above 1,024 bytes are compressed only when that method is nonempty. The concrete resolved endpoint, compression algorithm, server decoding, and regional routing are not available in the readable source. (.../core/Model/Network/NetworkConfig.lua:62-66; .../core/Model/Network/BI/BIManager.lua:52-54,71-96; .../core/Model/Network/Oper/OperManager.lua:84-100)

13. Failure handling, fallback, ordering, and deduplication#

13.1 Retry and backoff#

HttpManager scans saved requests on a ten-second cycle. Failed requests have their timeout doubled and their next-send time advanced. No reliable maximum backoff cap is visible. The replay loop increments a request count, but its apparent four-request check has an empty body and does not cap the number sent in a scan. A data-reset path can send and clear saved requests, which deserves runtime testing around account reset/logout. (.../core/Model/Network/HttpManager.lua:1-60,107-182; .../core/Model/Sync/SyncModel.lua:745)

13.2 Fallback route#

The initial BI request callback can attempt a fallback route on eligible error codes, except in mini-game builds. Test, global, and other builds select different fallback logic. Generic saved-request replays use HttpManager's callback and do not invoke BIManager.TryFallbackRequest. The report omits literal hosts/IPs because they are unnecessary to explain this routing. (.../core/Model/Network/BI/BIManager.lua:84-114; .../core/Model/Network/HttpManager.lua:138-168,195-215)

13.3 Ordering#

Client events receive sequential bi_id values, which can help reconstruct order downstream. However:

  • pending events are joined using Lua pairs rather than an explicit sorted traversal;
  • saved HTTP requests are also scanned with pairs;
  • retries can cause an older envelope to arrive after a newer one.

Therefore, a strict FIFO delivery guarantee is not evidenced. Analysis should use server receipt time cautiously and prefer client event time plus BI sequence where appropriate.

13.4 Deduplication#

No client-side content hash or duplicate-event suppression was found. A retried saved request reuses its serialized body/message ID, which is suitable for backend idempotency, but the client does not show whether the server enforces it. Purchase systems have transaction/order identifiers for business-level reconciliation, while generic gameplay events rely primarily on event identity and timing.

13.5 Sampling and rate limiting#

A scoped search of first-party BI, operational routing, and OneSDK-facing code found no explicit sampleRate, samplingRate, event-sampling, rate-limit, throttle, drop-event, or discard-event mechanism. This does not prove that no sampling occurs in native SDKs or backends. It means explicit client-side analytics sampling is not evidenced in the reviewed readable paths.

14. Remote configuration and server-controlled mappings#

The client is not the sole owner of analytics behavior.

14.1 Destination event mapping#

The operational response includes a JSON block stored under the legacy adjust key. OperBIManager indexes it by logical groups such as level-up and IAP, then emits the mapped AppsFlyer and Firebase event names. The server can therefore add or change selected external event names without an app release. (.../core/Model/Network/Oper/OperManager.lua:84-100; .../core/Model/Network/Oper/OperBIManager.lua:20-95)

14.2 Compression#

The same response can supply the BI compression method, changing wire behavior without changing the Lua implementation.

14.3 Consent and feature configuration#

Remote values control at least the ad privacy/UMP presentation path and various feature/social permissions. This makes server configuration part of the effective privacy and analytics design. A source review of the client cannot state which values were active for a given player/session.

14.4 Governance implication#

The effective analytics contract spans code and server configuration. Change control should cover:

  • mapping version and effective date;
  • owner and purpose for every AppsFlyer/Firebase event;
  • parameter schema and allowed types;
  • regional/consent eligibility;
  • deletion or deprecation behavior;
  • monitoring for mapping drift between external and first-party events.

19. Prioritized conclusions and recommendations#

Priority 0 — verify consent enforcement and backend idempotency#

  1. Instrument a clean-install network test for every regional build and consent outcome. Lua already calls first-party HTTP Send before the visible policy check; the test must determine whether that produces network egress and which identifiers it carries.
  2. Confirm that the first-party BI backend treats msg_id as an idempotency key. Test the accepted-request/lost-response case explicitly.
  3. Verify native consent enforcement for Firebase, BDA, and ads. In particular, check ad-manager initialization/loading before or during the UMP form and returning-user Firebase consent state.

Priority 1 — create one governed event contract#

  1. Maintain a registry covering first-party BI, AppsFlyer, Firebase, platform attribution, Crashlytics breadcrumbs, and ad-revenue events. For each event specify owner, purpose, trigger, fields, types, consent class, region, destinations, retention, and deprecation state.
  2. Version and audit server-controlled event mappings. Alert on unknown external event names, missing parameters, and mapping changes without an owner.
  3. Define cross-destination reconciliation keys for purchase, ad revenue, progression, and install events; do not rely only on event names or receipt time.

Priority 2 — reduce sensitive-data and diagnostic exposure#

  1. Review the optional device-information block and retire identifiers that are no longer necessary or reliable on modern OS versions.
  2. Audit purchase, SSO, Crashlytics, and project/error logging for access tokens, receipts, signatures, full URLs, raw server responses, and personal profile data. Add structured redaction at the logging boundary.
  3. Remove or constrain dormant high-risk APIs such as the broad LogSDKLogin payload if there is no documented production need.
  4. Treat push tokens and acquisition payloads as personal/linkable data in retention and deletion workflows; review the local Log.Info call that prints the raw push token and user ID.

Priority 3 — improve correctness and operability#

  1. Sort pending events by BI sequence before envelope creation, or formally document that downstream reconstruction must use sequence/time rather than arrival order.
  2. Add queue-health metrics: pending events, cached requests, oldest age, retry count, last successful disk save, serialization failures, and discarded/reset requests. Test a crash between Send and the database commit.
  3. Add schema validation for field names, types, required fields, and payload size—not only duplicate event-code checks.
  4. Document first-29-ID immediate flushing as an intentional onboarding policy, or replace it with an explicit named configuration.
  5. Record mapping/configuration version in every externally mapped event for reproducibility.

Final interpretation#

Gossip Harbor's analytics system is best understood as a first-party telemetry backbone surrounded by specialized acquisition, crash, platform, and advertising services. BIManager is the broad product-measurement layer; AppsFlyer is the confirmed named attribution partner; Firebase provides analytics-facing identity/events and Crashlytics diagnostics; UMP provides ad-consent presentation while native ad enforcement remains unknown; OneSDK abstracts native integrations; and server configuration dynamically changes some external routing. The client also has a pre-policy first-party send attempt and a save window before cached requests are committed. That division of responsibility is more accurate than describing the game as “using one analytics SDK,” and it avoids the unsupported claim that Adjust is present.
