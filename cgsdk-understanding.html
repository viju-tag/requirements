cgSDK 1.54.8: Technical and Integration Report

Report date: 27 October 2026
Package: com.coregame.sdk, version 1.54.8
Audience: developers and technical product owners integrating or evaluating cgSDK

cgSDK exposes several distinct systems: runtime configuration retrieval, experiment assignment, historical metric submission, content delivery, analytics, ad mediation, purchase reporting, and goal/competition modules. They share native platform services and initialization data, but their caches, persistence, and delivery behavior differ.

Here, managed code means the visible C# implementation; native code means the compiled Android/iOS libraries. This report describes the extracted 1.54.8 C# implementation and the Android/iOS bridge contracts. Game code appears only where it clarifies SDK consumption. Native libraries are included as compiled artifacts; backend targeting rules and native transport internals are outside the visible implementation. Source links identify the code behind each major behavior. Package metadata

1 Scope and evidence

The extracted package contains 348 files, including 67 C# files and 114 Unity metadata files. Its files were checked against the extraction inventory and remain unchanged. The Unity package version is 1.54.8; bundled Android and iOS components have their own version numbers. Those component numbers should not be used as the Unity package version.

The SDK directory is SDKExtract/com.coregame.sdk-1.54.8/. Game examples refer to the project's MergeFever/Assets/ files. Ten central integration files were also compared against the extracted GameIntegration copies and matched, including experiment overrides, runtime consumers, and the main-content handler.

The companion CGSDK_REPORT_SOURCES.json records the referenced files, source lines, and SHA-256 hashes. It makes the source snapshot identifiable if the project changes later. Findings about failure conditions below are derived from control flow; they are not results of device tests or live backend requests.

3 Initialization and shared configuration

Build configuration is separate from runtime configuration

Android uses the Resources/CoreGameSDK/CgSdkAndroidBuildConfig asset. Its fields include app name and Facebook identifiers. The Android prebuild processor requires the asset and nonblank Facebook app ID/client token, then writes or updates four CGSDK_* properties in the Gradle properties template. Missing required values fail the build. Android config type · Android generator

iOS uses Resources/CoreGameSDK/CgSdkIOSBuildConfig. The postbuild processor configures exported plist values, URL schemes, attribution entries, associated domains, entitlements, and linker/build settings. Ad Review setup requires its configured key and packaged injection resources. These are build inputs, not feature experiments or runtime payloads. Actual project keys and tokens are intentionally not reproduced here. iOS config type · iOS postbuild

Startup sequence

SdkManager.OnAwake() records install time if absent, invokes native initialization, creates the main-thread executor, initializes TrackingBridge, starts the periodic service, and restores main-content services. It then schedules a fallback initialization callback after five real-time seconds. TrackingBridge.Initialize() restores live tracking state and checks session rollover before starting the managed custom-event queue. SDK startup · Tracking initialization

Native initialization supplies a pipe-delimited configuration. GameCallbacks.HandleCoreGameSDKInitSuccess() stores the identity/context fields and user tracking fraction in SdkManager and PlayerPrefs, then explicitly calls PlayerPrefs.Save(). Optional event thresholds and hardcoded experiment assignments populate separate in-memory maps:

Field Role visible in C#
Game ID and client/platform ID Identify the game and client in tracking payloads
User ID Identifies the player; must be nonempty before managed uploads
Company name and build number Identify the deployment in tracking payloads
Country, calendar day, UTC offset Context attached to tracking
User tracking fraction Input to custom-event sampling
Optional event-threshold map Configures sampling by custom-event name
Optional hardcoded experiment assignments Populates the hardcoded experiment dictionary

The presence of country or calendar-day fields does not establish that any particular experiment targets those attributes. Their use for targeting remains a native/backend question. Initialization payload

Initialization is accepted once

The callback sets InitSucceeded before scheduling configuration processing on the main thread. Later initialization callbacks return immediately. The five-second fallback reconstructs the nine persisted identity/user-fraction fields, but not the optional event-threshold map or hardcoded experiment assignments.

Consequently, if the fallback wins, this handler ignores a later real native initialization payload. On a fresh installation, the fallback can contain an empty user ID; the managed tracker then holds uploads while that ID remains empty. This is a conditional source-level failure scenario, not a reproduced device result. Fallback implementation · One-shot guard · Upload identity gate

4 Runtime configuration framework

Public contract

CgSdkRuntimes.Instance.GetRuntimeData(runtimeName) returns a string. The wrapper does not impose a JSON schema or interpret fields. The consumer owns parsing, validation, and fallback decisions.

The C# implementation maintains an in-memory concurrent dictionary keyed by runtime name. A value is reused while its age is less than 300 seconds. On a miss or expired entry, it calls the native platform API and stores the returned string with the current timestamp. This is lazy expiration on access, not a background refresh timer. Runtime cache

Android calls com.ads.sdk.supplemental.runtime.Runtimes.getRuntimeDataForGame. iOS imports the corresponding native function. Caught bridge failures return an empty string; the iOS wrapper also handles a null pointer and frees a returned native string. Android runtime bridge · iOS runtime bridge

Empty responses and refresh limits

Empty native results are cached for the same 300 seconds as valid payloads. A consumer that retries rapidly can therefore receive the same cached empty response until the entry expires. The facade exposes no explicit cache-clear API and performs no C# disk persistence.

The wrapper does not reveal whether the native result came from memory, disk, or a recent network request. It also does not establish the native fetch interval, endpoint, retry policy, or targeting rules. The 300-second value describes only the C# cache.

5 A/B test framework

Server-managed experiments

The public API is GetExperimentVariant(expName, codeVersion). C# asks native code for an allocated integer variant. Android calls ExperimentManager.getChosenVariantForGame; iOS imports a native function of the same purpose.

Cached results are reused while they are less than 300 seconds old; the next read at or after that age calls native code again. The dictionary is keyed only by experiment name. Although codeVersion is forwarded on a native call, changing it does not bypass a cached result for that name. Control is integer 0. Caught native-call failures return control, which can also be cached. Experiment facade · Android allocation bridge · iOS allocation bridge

The wrapper does not show a random draw, bucketing hash, traffic allocation percentage, eligibility rule, or assignment persistence policy. It exposes the selected result. Nothing in this facade establishes whether reassignment can occur between sessions or after a configuration update.

Game mapping and local overrides

The game converts positive integers into names such as AB1 and AB2; zero or negative results become CONTROL. It passes an empty code-version string in the inspected adapter. Before contacting cgSDK, ABTestHandler checks a locally saved override. An explicit setter saves overrides to ABTestPlayerData.json; the ordinary SDK read does not save its returned assignment into that override file.

For example, the energy feature requests experiment game_energy_shop, then selects the corresponding ABTestType entry from its feature-config list. The feature-configuration list and the experiment assignment are separate inputs. Its unmatched-variant fallback is the first list entry, not an explicit search for a CONTROL entry. Game experiment adapter · Energy selection example · Configured experiment ID

The debug selection screen saves overrides and restarts the game to apply them. A persistent debug override can therefore explain why a test installation disagrees with the SDK's native assignment. It is a game-owned override, not proof that cgSDK's allocation changed. Debug apply behavior

Hardcoded experiments

Hardcoded experiments use a separate path:

  1. The game may provide a definition string through GetHardCodedExperimentsFromGame, documented as name:version:variants_info;....
  2. Android initialization forwards that string to native code. The visible iOS initialization call has no equivalent config argument.
  3. The native initialization payload may return name:variant;... assignments.
  4. UpdateHardcodedExperimentsData() updates a separate session dictionary.
  5. GetHardcodedExperimentVariant(expName, codeVersion) returns the dictionary value or control.

This getter does not use codeVersion and has no TTL check. Updates do not clear the dictionary first, so omitted entries remain. A parsing error can leave assignments processed before the error already updated. No game C# subscriptions or calls to the hardcoded experiment APIs were found in the inspected project. Historic Data Segmentation API

CgSdkHistoricData explicitly exposes the SDK's historical metric ingestion interface. A GameMetric contains:

Field Meaning
metric Required metric name
s1 to s5 Optional string dimensions
d1 to d10 Optional nullable double measures

TrackGameMetric(metric) submits one metric; TrackGameMetrics(list) submits a batch. Both return void. There is no success callback, segment result, or query API in this facade. Data is forwarded outside the Unity Editor to the Android JNI or iOS native bridge. Historic metric API

The wrapper rejects null metrics, empty names, and reserved characters in the name or string dimensions. The reserved characters are caret, comma, pipe, NUL, and semicolon. Any invalid item rejects an entire batch. Name validation checks null/empty, not whitespace-only content; numeric range and finite-number checks are not implemented here.

Serialization uses caret-separated fields and semicolons between metrics. Null fields become empty positions; doubles use round-trip formatting with invariant culture. These details matter because this is a positional native protocol, not a dictionary of arbitrary named properties. Validation and serialization

No calls to CgSdkHistoricData, TrackGameMetric(s), or construction of GameMetric were found in game C# under either the live project or extracted integration. This establishes that custom game-side use of this API is absent in the searched code; it does not rule out historical tracking internal to native SDK components.

Eligibility supplied by native code

Main-content callbacks can enable content infrastructure for a player, deliver levels, invalidate levels, and change cache capacity. The C# wrapper consumes those decisions; it does not calculate the underlying audience criteria.

The game's interstitial integration also explicitly delegates payer/nonpayer handling to the SDK, while keeping a local unlock-level check. That comment and code identify the ownership boundary, but do not reveal the native payer rules or whether a particular player currently qualifies. Native content callbacks · Interstitial eligibility example

What remains inside native code or the backend

The available source does not establish exact audience conditions, spend windows, country/cohort rules, weighting, bucketing, cross-device assignment, reassignment, or whether historical metrics drive a particular experiment. Those questions require the native implementation, configuration definitions, or backend documentation. Runtime values and experiment integers alone are insufficient to reconstruct those policies.

7 Content configuration and caching

Main content

CgSdkMainContent.GetLevelData(levelNum, currentLevelNum) returns null when content infrastructure is off. On a cache hit, it returns level data plus local asset paths. On a miss, it asks native code to fetch and returns null immediately. It does not wait for a download or select packaged game content on the caller's behalf. Main-content lookup

The default cache cap is three levels. Native callbacks may supply a positive replacement cap, add/update level records, or drop named levels. Level data, asset-directory information, and the cap are restored through PlayerPrefs. Saved level records use level|data|assets|restart fields joined by carets; the deprecated restart field remains relevant when restoring older data.

The implementation handles callbacks that arrive during startup restoration, including early drops and capacity updates. Save snapshots are generation-checked so older queued saves do not overwrite newer state. However, normal trimming after a delivery removes at most one lowest-numbered cached level; a multi-level delivery can leave the cache above its configured cap. A cap update does not immediately trim existing records, and adding one new level while removing one old level can preserve that surplus. Content restore · Content saving · Capacity updates · Delivery and trimming · Invalidation

GameContentHandler provides a game-owned fallback policy: it can use SDK content, previously saved SDK level data, or bundled content depending on eligibility and availability. The SDK lookup itself does not select these fallbacks. Game content example

Content catalog

CgSdkContentCatalog.GetCatalogItem(key, index) performs a synchronous native read and returns @-delimited key=value text. The contract returns an empty string for missing/unavailable items. The Editor path returns an empty string.

This facade has no C# TTL, fetch API, invalidation method, or persistence layer. The 300-second runtime/experiment cache does not apply to this catalog interface. Catalog contract

TrackingBridge.SetExtraParameter forwards a key/value to the live summary trackers. Each tracker recognizes its own keys. The operation is key-specific: for example, interval screen-view handlers increment by one even if a larger integer is supplied, while wallet/time handlers assign the supplied value. Currency information uses CurrencyInfo: currency name, start value, free earnings, IAP earnings, spending, and final value. Tracker serialization converts this into positional strings. Currency model

Puzzle and session lifecycle

A level start creates a live puzzle tracker unless tracking is not initialized or a puzzle tracker already exists. Completion/failure fills the puzzle result and duration, collects the summary, clears the live puzzle, updates session/interval counters, and saves live state.

After at least 1,800 seconds since the recorded pause, the bridge marks any live puzzle as a drop-off, collects the previous session summary, and creates a new session. The lifetime session count increments, the daily count increments or resets for a new day, and the per-session puzzle count resets. The live puzzle tracker remains. A fresh installation creates an initial session while restoring local state. Puzzle lifecycle · Session rollover

On application pause, the bridge records pause time, updates session elapsed time, requests the game's interval data, collects the interval summary, saves live state, and hands off remaining native-bound records. The interval callback lets the game populate its fields before the SDK serializes them; the SDK then replaces the interval tracker. Pause handling · Interval collection

PeriodicRepeater is implemented in Supplemental/Util.cs. It waits Task.Delay(60000, token) before each interval collection, starts on SDK awake/resume, and cancels on pause/destroy. This is a nominal 60-second async delay independent of Unity time scale; scheduling or application suspension can still delay execution. Resume starts a fresh wait. The interval tracker's 30-second comment does not match the executable schedule. The 1,800-second session boundary is separate. Periodic scheduler

Native handoff and serialization

Puzzle and session records are colon-delimited. Interval records use a shared:sessionNSec: prefix, but still follow the native summary route. A record's textual prefix does not determine its transport.

TrackingBridge.CollectTracking() joins records with carets, passes them to native when forced or when the buffer exceeds 500 characters, and clears its C# buffer. Android calls TrackerController.updateInPendingTracking; iOS calls the corresponding native function. The source comment mentioning 1,000 characters is stale; the actual comparison is > 500.

The bridge wrappers catch and log errors but return no handoff acknowledgment. The C# caller clears the buffer even after a caught native-call error. Native storage, retries, network endpoints, acknowledgment handling, and sampling cannot be inferred from this boundary. Collection threshold · Android tracker bridge · iOS tracker bridge

Live puzzle/session state is written to PlayerPrefs. The pending serialized summary buffer itself is not included in that state, and SaveLocal() does not explicitly call PlayerPrefs.Save(). A small completed summary can therefore remain only in C# memory until handoff. Live-state saving

9 Custom analytics events and managed delivery

Event schema

SharedTracker supplies Parent, string slots S1 through S40, and numeric slots D1 through D10. In the inspected game, S1 is the custom event name and Parent groups related events.

The SDK overwrites S39 with build number and S40 with calendar day. These two fields should not hold game-specific payload values. It replaces colon and caret characters in the string slots, then serializes:

shared:Parent:timestamp:S1:...:S40:D1:...:D10

Parent is concatenated without passing through the same sanitizer. Numeric values use invariant-culture formatting. The event is handed directly to CgSdkTracker; it does not pass through TrackingBridge.CollectTracking(). Custom event implementation

Sampling

Before serialization, SendTracking() applies this condition:

If userTrackingFraction > thresholdFor(S1), drop the event.

The threshold map is encoded as eventName=integer:eventName=integer. Updating it replaces the map. An unconfigured event has threshold zero. No fresh random draw per event is visible here, and the integer scale is not documented by this code; it should not be described as a specific percentage.

The user value and event thresholds arrive through native initialization or a later tracking-fractions callback. These sampling values control custom-event collection, not feature assignment. Sampling decision · Threshold map · Sampling update callback

Persistence and upload

An event that passes sampling is offered to the managed queue. If the queue is not initialized, the call is dropped. If initialization has started but restoration is unfinished, the event is buffered temporarily. Once ready, the queue appends events and saves them to Application.persistentDataPath/cgsdk/trkuni.json.

The scheduler and throttle use Unity's scaled timing through InvokeRepeating and Time.time. These intervals are not guaranteed wall-clock delays when game time is paused or scaled. The initialization fallback described earlier instead uses real-time waiting.

The envelope has action sync, category tracker, and a data object containing game/client/user/company/build/country/calendar-day/UTC-offset context plus the encoded event batch. The field named cohort is populated from CalendarDay; this mapping does not establish an experiment cohort. Queue initialization · Queue scheduling and request · Payload construction

HTTP failure or an invalid/non-success response normally leaves the queue for another scheduler attempt. Successful responses are expected to report a synced count. There is no explicit per-event idempotency protocol in the inspected code; an accepted request whose response is lost can be retried, so exactly-once delivery should not be promised.

Pausing the application does not trigger an immediate managed-queue upload; the queue's application-state handler is empty. Events already saved to disk remain available for later upload. Corrupt or unreadable stored data is discarded during restoration. Queue restoration and storage · Response handling

Concrete game example

When an order completes, the game creates a SharedTracker with Parent = "game_features" and S1 = "order_complete". It supplies level in S2, ordered items in S3–S5, order type in S7, currency data in S8, and remaining-order counts in S9. It calls SendTracking() and resets its order-currency tracking.

11 Ad handling by format

Mediation initialization and ownership

AdsNative exposes four formats: banner, interstitial, rewarded video, and app-open. These are the formats available through this Unity facade; it has no separate native-ad, MREC, or rewarded-interstitial API. The word native in AdsNative refers to the platform bridge, not a native-ad format. Public ad API

Mediation has its own initialization entry point, InitialiseMediationSDK(installTimestamp, testMode), and completion event, OnMediationSdkInitialised. Android forwards the timestamp and test-mode flag as JSON to com.ads.sdk.ads.Mediation; iOS passes a callback delegate and test-mode flag, without that timestamp argument. The game's AdsController.Initialize() subscribes before calling this entry point and gates its ad methods on mediation completion. In the Editor, that game adapter marks itself initialized without native mediation. Core SDK identity initialization described in section 3 is a separate callback path. Android bridge · iOS bridge · Game mediation initialization

The visible C# API has no explicit load, preload, destroy, retry, network-selection, ad-unit-selection, or per-request placement argument. Availability and show requests cross into native mediation. Consequently, waterfall/bidding behavior, automatic reloads, retry delays, native frequency caps, and network-specific failure details cannot be established from this C# source. A returned show boolean is not proof of a displayed impression or earned reward; later callbacks carry those lifecycle signals.

Interstitial behavior and game-owned cooldowns

Native mediation reports interstitial availability through HandleAdPlacementAvailability; the C# callback dispatches available or unavailable without an error code. The game keeps an availability flag, resets it when requesting an ad, and updates it from those events. The outer game manager rejects unavailable interstitials and disables them for remove-ads owners. Initialization also applies a calendar-day waiting period and first-session delay. The show path applies tutorial checks, an unlock level, enabled placement triggers, and a cooldown flag. Its runtime configuration comes from game_it_ads_cd, described in section 4; payer/nonpayer decisions are explicitly delegated to the SDK by the integration comment. The game maps META_IT, OUT_OF_ENERGY_IT, ORDER_SERVE_IT, and ON_LEVEL_COMPLETE_IT to configured trigger flags. These names describe game locations and analytics context; the native show call receives no placement string. After completion or display failure, the attached game action starts delayBetweenInterstitialAds. Closing a rewarded ad starts the separate delayBetweenRewardedVideoAndInterstitial timer. These timers belong to the game; they do not document native mediation's own caps. Game triggers and cooldowns · Rewarded close handling

If configured with an ad-break reward, the game shows its popup and delays the show request by one second. It attaches the popup's success action to interstitial completion, which runs on OnInterstitialAdHidden. This is a game-owned reward policy: cgSDK's interstitial hidden callback supplies no completion/reward boolean. Rewarded video and reward delivery

The SDK forwards the native grantReward result through OnVideoAdHidden(bool). Android receives a boolean; iOS reads the first #-separated field and treats exactly "1" as true. C# does not calculate eligibility, reward quantity, or reward type. It supplies no separate public reward-earned event, transaction identifier, or reward deduplication mechanism in these handlers. Reward callback · Android callback adapter · iOS callback decoding

The game stores the pending RewardAdData, clears its availability flag, and calls the SDK show method. On device, OnVideoAdHidden(true) calls GrantReward(), which invokes that request's adCompletedAction; false closes the flow without that completion action. OnVideoAdDisplayFailed invokes adFailedAction. The Editor shortcut calls completion immediately and therefore does not validate the device reward flow. 12 Puzzle Master framework

Puzzle Master is a stateful goal-and-reward module implemented partly in C#, unlike the runtime/experiment facades. Native code supplies the day's timestamp, FTUE flag, total progress, current-goal progress/index, and goals. Each goal has Target, opaque Reward, UIReveal, and ClaimStatus; statuses are 0 (not ready), 1 (ready to claim), and 2 (claimed). Native payloads use & between goals and @ between each goal's four fields. The callback replaces the current list and treats a nonnegative current-goal index as started. Malformed short goal entries are skipped; integer parsing falls back to zero. GetGoalsData() returns the mutable list, not a copy. State loading · Status constants

HandlePuzzleMasterProgressUpdate(increment) does nothing until started. Otherwise it adds to total progress, fills the current goal, carries surplus into following goals, and marks each crossed goal ready to claim. Each crossed goal sends the updated progress/index and &-joined claim statuses to native code. The method does not reject negative increments. The score-bearing LevelNative.OnLevelComplete overload calls this method, but the inspected game also feeds merge-task values directly, after applying a game-owned booster multiplier. Avoid double-submitting the same earned progress when integrating both routes. Progress algorithm · Merge integration

The SDK separates goal completion from granting a reward. OnGoalClaimed(goalId) marks an in-range goal claimed, but does not check that it was ready, deliver currency/items, or immediately send the claim to native. The game's OnGoalClaim() grants its parsed reward first and then calls this SDK method. The game owns reward parsing and actual inventory changes. OnPuzzleMasterScreenClosed() forwards the complete progress/claim snapshot; SdkManager.OnPause() calls internal SaveData(), which also forwards a snapshot to native. There is no C# disk/PlayerPrefs store for this module, so native persistence durability cannot be inferred here. Claim and screen calls · Save bridge · Game claim ordering

OnPuzzleMasterFtueViewed() clears the local FTUE flag and notifies native. OnPuzzleMasterScreenViewed() clears auto-trigger and notifies native. The day timestamp is exposed for the game to interpret; this C# module does not itself run a midnight-expiry timer. Native auto-trigger callbacks set a flag for the game to check. Android and iOS both provide Puzzle Master bridges; the iOS callback adapter decodes six pipe-separated fields before loading state. No dedicated Editor simulator is present in the facade. View calls · iOS callback decoding

For expiry, native sends reward strings. C# sets ShouldGrantRewardsOnExpiry true and schedules GrantRewardsAndReset(string[]) on the Unity main-thread executor. Nonempty data splits on &; empty data becomes a one-element array containing an empty string. The SDK event does not itself grant rewards or reset all progress. MarkRewardsGrantedOnExpiry() only clears the local flag. The game waits for managers, parses rewards, adds them to inventory, clears this flag when parsed rewards exist, and reinitializes its UI. Its empty/unparseable reward branch does not clear the SDK flag, which can leave its subsequent initialization blocked by that flag. Treat this as a source-level edge case, not a reproduced device failure. Expiry callback · Game expiry flow

14 Daily Puzzle retrieval

CgSdkDailyPuzzle.GetDailyPuzzle(useUtc) computes today's yyyyMMdd using UTC or the device's local date. If PlayerPrefs contains matching CGSdk_DailyPuzzleDate and nonempty CGSdk_DailyPuzzleData, it returns the saved string without contacting native code. Otherwise Android calls com.ads.sdk.impl.content.DailyPuzzle.getDailyPuzzleData(useUtc). The Android bridge logs exceptions and returns an empty string. The iOS retrieval branch is unimplemented and leaves the result empty. Daily retrieval · Android bridge · Date calculation

Every attempted fetch saves its date and payload through PlayerPrefs, but does not explicitly call PlayerPrefs.Save(). Empty payloads are not reused by the hit condition, so another call retries. A valid same-date payload has no C# refresh/invalidation API. The cache key does not include useUtc; switching modes when both resolve to the same date can reuse the earlier mode's payload. The SDK returns opaque content and does not implement a game UI, reward flow, or completion tracker here.

In the Editor it loads Resources/CoreGameSDK/CgSdkDailyPuzzleConfig and returns puzzleData. Missing configuration is dereferenced without a null guard. The same PlayerPrefs cache check happens first, so a previous same-day cached value can hide edits to the Editor asset. No CgSdkDailyPuzzle calls were found under the live game's C# assets; this is a package capability, not evidence of an enabled game feature. Daily retrieval

IapNative.SendPurchaseInfoVerified reports a purchase already confirmed by the platform store; it does not initiate a purchase, grant an entitlement, restore purchases, or return a verification decision. The method and both platform adapters return void. Its documentation asks callers to report once after store confirmation. C# supplies no deduplication, durable retry queue, success/failure event, or receipt-verification result. As noted in section 10, local revenue increments precede native processing. Both price strings are parsed through StringParseToDataType.ParseGameSuppliedCurrencyToDouble: remove characters other than digits, dot, comma, minus; replace every comma with dot; parse NumberStyles.Float under invariant culture; log and return zero on failure. Lifecycle and callback execution

SdkManager.OnAwake, OnPause, and OnResume are explicit integration methods, not Unity's ordinary Awake and OnApplicationPause message names. The game's analytics handler forwards lifecycle events to them. Pause stops the periodic service, collects tracking, saves Puzzle Master, calls native pause, and saves main content. 20 Source findings requiring care

The following conditions follow from the implementation. They are not fixes applied to the package, and they have not been reproduced against the backend or on a device.

Finding Condition and consequence Evidence
Fallback initialization can win permanently If fallback wins the one-shot guard, later native initialization is ignored; an empty user ID blocks managed uploads. Fallback, guard
Zero synced count clears the managed queue For a response with s=true, a=sync, c=tracker, and a non-null data object, CleanSyncedTrackings removes a prefix only when 0 < sc < currentQueueCount; other values clear the whole queue. Zero or omitted sc can discard pending events. The count is not checked against the dispatched batch size. Cleanup, response
Managed queue file replacement has a loss window Save writes a temporary file, deletes the live file, then moves the temporary file. Interruption between delete and move leaves no live file; startup does not recover the temporary file. This is not an atomic replacement despite the comment. Storage
Native handoff is not acknowledged to C# A caught bridge error can lose pending summaries because the caller clears its unpersisted buffer. Collection, bridge
Custom events before queue initialization are dropped The queue's enqueue method returns when _initDone is false. A new-session callback can occur during bridge restore before managed queue initialization. Initialization order, enqueue gate
Runtime/experiment fallback values can persist for five minutes Cached empty/control results delay recovery even when consumers retry rapidly. Runtime cache, experiment cache
Code version is absent from experiment cache keys Changing codeVersion does not bypass the server-experiment cache; the hardcoded getter ignores it. Experiment implementation, hardcoded getter
Custom Parent field is not sanitized A colon or caret in Parent can disrupt positional encoding. Shared event serialization
Historical metric validation is limited Whitespace-only names and nonfinite numeric values are not rejected by this facade. Any invalid string field rejects the whole batch. Historic validation
